# Operation Map Helipad Read Model Binding

## Scope

The existing `BuildingFactionProductionSpawnPointReadModel` publication now binds runtime helipad slots to immutable helipad anchors from the active loader-neutral operation-map metadata. This slice does not add map loading, Addressables, scene changes, editor generation, or a second occupancy authority.

## Runtime Behavior

- Active-map helipad anchors validate faction/lane identity, duplicate ownership, finite geometry, positive clearance, runtime-grid containment, and one exact runtime production-slot owner.
- Matching runtime helipad rows retain their building runtime ID and slot index, preserving existing reservation and occupancy behavior.
- The matched landing row is snapped to the exact active-map helipad center and grid cell.
- A faction with active-map helipad anchors no longer exposes unbound building-derived helipad fallbacks.
- Helipad rows for factions without map anchors and non-helipad production rows remain unchanged.
- No-active-map behavior is unchanged.
- Invalid or ambiguous active metadata fails closed without partially applying map positions; the production publisher clears the boundary buffer rather than exposing stale mixed ownership.
- Existing map-generation dirty invalidation republishes the production-slot buffer on activation, replacement, and teardown without a new update loop.

## Architecture And Performance

- Immutable map identity and placement stay in `OperationMapBlob`; mutable slot reservation and occupancy stay in the existing runtime building/read-model owners.
- Binding uses fixed-capacity unmanaged lists and nested scans only when the existing building read model is dirty; it adds no per-frame managed allocation.
- No manager, controller, facade, service locator, update-loop `MonoBehaviour`, delivery dependency, or broad replacement system was introduced.
- The frozen building composition owner remains within its accepted source-growth byte budget.
