## Findings, ordered by priority

### P1 — Unit combat is disabled by contradictory ownership rules

`SkirmishScenarioSpawnSystem.cs:368-369` adds `CampaignMissionCombatSuppressedTag` to every registry-spawned unit. Shared `UnitEngagementSystem.cs:51,71,164,183` and `UnitAttackSystem.cs:143` exclude that tag. However, `SkirmishExpandedEngagementService.cs:60-64` regards registry units with `UnitAttack` as using shared combat and assigns no combatant target. The expansion still damages an explicitly ordered structure through `OrderedStructure`/`ApplyShot`.

Thus the normal prefab-unit path has no unit-versus-unit damage owner, while objective structure damage can still occur. A base-destruction victory cannot establish working counters, infantry screens, AA or meaningful army combat. This is a source-confirmed integration defect, not a claim that this audit observed every unit fighting. Resolve ownership through one fog/domain-aware shared combat boundary and test registry-backed opposing units, structures, hidden contacts and AA. Do not simply remove suppression without restoring the intended fog/domain policy.

### P1 — Construction reads a different economy from the displayed stock

Live reproduction: Main Menu → Skirmish → search S003 → select → Start Match → Build. HUD showed 450/800 Materials, 120 Oil, 350 Fuel. Build showed 450/800 Materials but 0 Oil/0 Fuel; Barracks (90), Depot (100), Fuel Bladder (40) and Guard Tower (50) were all locked as `Insufficient materials`; Place was disabled. This prevents the advertised buildup and defense loop.

Immediate same-Editor comparison: S001 opened with 220/600 Materials; the same four construction cards were available and Place was green. Its Build fuel agreed with the live usable stock (152 at observation), rather than becoming zero.

The integration split is visible in source: `SkirmishSessionInitializationSystem.cs:82-90` initializes separate `SkirmishEconomyStockComponent`; `UiMatchHudResourceReadModelSystem.cs:51-54` projects that into the header. Normal construction affordability/spending uses `FactionTacticalMaterialsComponent` (`FactionConstructionResourceUtilitySystemHelper.cs:10-26`), and expanded production reads/writes its separate stocks (`SkirmishProductionService.cs:592` onward). Reconnect request acceptance, spending, refunds, stock display and logistics to a single authoritative shared economy. A display-only correction is insufficient.

### P1 — ARIA secretly issues orders outside the visible input route

`AriaSkirmishStructureOrderSystem.cs:34-45` calls `TryOrderStructureAssault` each update for expanded sessions whenever any ARIA phase is not Manual. `SkirmishExpandedPresentedOrders.cs:122` onward selects every living structure-assault group and directly issues orders, without requiring a squad selection, presented control or completed touch. The class comment explicitly says it runs when the tap does not land.

This breaks human/ARIA parity and can mask failures in the visible planner. It can also overwrite a group order continuously while ARIA is active. Remove the out-of-band order mechanism; make the actual presented command route reliable and record its provenance. Verify Stop/takeover cancels future input and that camera guidance never creates a troop order.

### P1 — The air mission's intended public progression is not connected

The selected S003 briefing tells the player to build a Helipad and transition to attack helicopters. Live Build offered the four legacy buildings, with Aircraft unavailable; clicking Aircraft did not change the screen. No R2/Helipad transition was available in the inspected surface.

ARIA's contracts declare `RecruitAntiAir` and `AirPad`, but a source search found no assignments to either target in production scripts. `AriaSkirmishPlanSystem.cs:459` also requires `AirQueueOffered && !PadReady`, while `SkirmishAriaPublicProjection.cs:82-85` only sets AirQueueOffered when PadReady is true. The pad branch is therefore unreachable under that projection. The declared air capability is not equivalent to a playable air loop.

Connect paid R1 AA, readiness, Helipad construction, air queues and actual attack/return/landing/refuel to the human UI and the same ARIA observation/input path. S003's scenario brief explicitly requires affordable return/refuel (`Scenarios/DB_BA.md:76`). Air lifecycle acceptance remains pending; this audit did not produce or fly aircraft.

### P1 — Starting structures bypass the shared building/logistics pipeline

`SkirmishScenarioSpawnSystem.cs:438-479` creates bare entities with identity/faction/producer metadata. `SkirmishVisualSpawnService.cs:165` supplies instantiated visual GameObjects. This does not submit `BuildingRuntimeSpawnRequest` as S001's startup does (`InitialUnitsSpawnSystem.cs:1216-1230`). The S003 handoff itself records that extraction, physical haul and refinery/fabrication do not run on these facilities.

The architecture contract requires shared spawn boundaries and shared production/economy (`TECHNICAL_ARCHITECTURE.md:91,108,114`). Rebind designated objective roles to the resulting real building entities after shared spawn completion; preserve placement, footprint, production, damage, destruction, logistics and cleanup ownership. A visible yard is not a working supply chain.

### P1 — The counted ARIA evidence cannot certify input compliance

`SkirmishS002AriaRunHarness.cs:595-596` writes InputViolations and HumanInterventions as literal zeroes instead of measured counters. The retained trace records phase/clock/base health, not a complete input provenance stream. Combined with the background ordering above, `countedWin=1` does not prove legal visible input.

S003/runs.csv contains two startup-timeout aborts and one English seed-104732 victory at 240.755 s. Preserve all three rows. The required 104732/130366/155924 × EN/FA coverage and at least two real wins per locale are missing. Add measured intervention/violation events and bind each counted run to the actually tested code/config; rerun after integration repairs. Do not overwrite the failures or reuse this win as post-fix evidence.

### P2 — Briefing and opening composition do not describe the live mission

The native selected S003 setup continued to show `Normal · 15-minute limit` and the legacy two-rifle/one-car/supply rules. Actual S003 started with an 18-minute clock, 12/48 infantry and a rocketeer card. The S003-specific advice is confined to a one-line footer that visibly truncates at the helicopter instruction. `SkirmishSetupPrefabBuilder.cs:270` authors the static legacy summary; `QuickCustomScreenView.Scenarios.cs:155-181` updates the short description without making the full rules pane reflect the compiled setup.

S003's opening camera framed large hangar scenery and a decorative aircraft; its army was not visible in the central play area. S001's opening framed visible infantry, vehicle and base facilities. S003's cards were grayscale even while populated, and the Car card used the infantry image. The shared typography, colored command buttons and ARIA portrait are reused successfully, but these defects undermine orientation and state readability. `Watch ARIA — preview` also remains prototype wording.

Bind briefing/HUD/guide to the same resolved setup; show the next achievable action, identify real base/army, and give roles correct visual states. Any substantial redesign must follow the repository's reference-mockup and visual-review gate before implementation.
