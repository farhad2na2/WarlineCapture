## Intended UI ownership in matched source

`MainMenuPlayUI.cs:502-574` classifies the squad tray as gameplay UI through its containment check. In normal input, `HandlePointerPressed` (`RtsSelectionRuntimeInputCompositionSystemHelper.cs:272-323`) latches that UI-origin decision through `BeginPointerPress`, clears camera dragging, and only arms normal/command pan for a world-origin press. Moving off the tray does not by itself clear the latched owner.

The same helper's held Select and transport-selection branches explicitly test `!PointerPressedOverUi`; scan preview does too. Release checks the original UI owner OR release-over-blocking-UI before world-target actions (`:389-420`), clears drag/selection fields, and returns. Thus a classified UI-start swipe must not issue world release orders, even when it ends outside the tray. Cancellation runs before these handlers (`:174-179`), clears queued move/release/drag state and returns; it is not a world release.

Card relay routes real potential/begin/drag/end callbacks to its ScrollRect (`MatchHudSquadCardPressRelay.cs:19-31`); begin-drag marks the press ineligible for click, cancels the captured group and sets `Dragged`. Roster callback checks that flag and stable pressed-group identity (`MatchHudSquadTrayView.Pagination.cs:263-285`). The card press does not itself prove global runtime pointer capture; the tray containment and runtime latch are independently necessary. Navigation checks actual viewport, safe area and matching top ScrollRect ownership at both endpoints (`MatchHudSquadTouchNavigation.cs:195-241`). These preflight checks are not a live guarantee of contact ownership throughout the drag.

`AriaTouchInputUiSystemHelper.cs:97-145` separates actual moved samples and release across UI opportunities; Stop removes the owned device to avoid a synthetic canceled-touch click. `GamePointerInput.cs:38-79` broadcasts device-removal/touch cancellation for that frame; its returned state carries no pointer ID. Correct shared lifecycle/update ordering therefore deserves real InputSystem/EventSystem coverage. This review did not run it.

## Concrete conditional dragging seam

The held-pan branch at `RtsSelectionRuntimeInputCompositionSystemHelper.cs:371-374` tests shared `GetCameraDragging` and nonzero movement, without explicitly checking UI-origin. Normal UI press resets the flag, so this is **not a demonstrated normal-path leak**. A concrete synthetic condition is: classified UI-origin press, selection mode inactive, capture-ignore route absent, then a distinct writer sets the shared drag flag true before the next held sample. That sample reaches Pan despite its UI latch. A true flag existing before the press should be cleared by the normal press; pre-press stale state alone is not enough.

`RtsSelectionRuntimeCameraSystemHelper.SetCameraDragging` (`:219-231`) blocks true under tactical Follow, but has no UI-owner test; `PanCamera` (`:207-216`) checks Follow ownership and queues Pan, with no additional UI-origin check. Other real write paths include fullscreen ISO (`:439-465`) and support-targeting (`RuntimeInput:182-196`). The fullscreen path checks current UI hit and normally returns false from the camera tick before normal pointer processing (`RuntimeCamera:155-163`; `SelectionGameplayStartup:650-658`): this is **mode-exclusive**, not evidence of two simultaneous normal writers. Support mode likewise returns early and arms from a new press outside any UI. Mode transitions or skipped press/cancel handling could matter, but are not observed in the saved screenshot evidence.

The explicit capture route also matters: `CaptureUiClickSequence` sets UI/ignore flags but does not clear the camera flag (`RtsSelectionInputCompositionSystemHelper.cs:375-390`). `UpdateNormalPointerInput` early-returns while that capture is active (`:214-223`), so it does not directly fall into held Pan. `CompleteCapturedUiClickSequence` (`:262-270`) clears ignore/suppression fields but not UI-origin/dragging; the next ordinary press resets these. Cancellation clears release/drag fields, while capture flags settle separately. These are lifecycle fixture targets, not proof of a stale flag causing this run's camera movement. Missing pointer input returns early rather than providing cancellation, so device-removal broadcast must actually reach the runtime update.

## Smallest conditional defense and fixture

If the independently reviewed stress fixture establishes a worthwhile defense, the smallest local pan guard is an explicit UI-origin exclusion alongside `GetCameraDragging` in the held-pan branch. This would defend the synthetic post-press writer case and should leave intentional world-origin camera drags working. It would not fix a missed initial UI hit/latch, a writer calling Pan through another path, missing lifecycle cleanup, or the unproven blank-sand cause. No implementation is supplied or authorized by this report; do not silently reset all camera modes or disable world input.

`fixtures.json` proposes a small joint runtime-input plus real EventSystem/ScrollRect fixture: UI swipe lifetime, explicit stale/post-press flag stress, cancel/device removal/mode return, and a positive world-drag control. Extend existing UI fixtures rather than repeating their visual/card geometry tests. Assert Pan requests and world-command buffers/accepted receipts as well as camera pose, and pump actual separate contact frames. Current UI-only swipe success is not evidence of no runtime camera pan or orders.
