# Pipeline eval_file protocol review

Source-only review at `dd4a5bca3ed3c8988efc51e4a37ecdfe49890b5d`. Installed package: Pipeline 0.6.0-exp.1, cache 9bb4172c603c. Fourteen exact package files and the installed Mach-O CLI binary are pinned in source-pins.json. The CLI install path says beta.9; it was not invoked and no CLI source ships beside it. Windows package raw equality and Mac live wire behavior remain untested. No Editor, eval, compiler or native operation was run.

Windows reread its actual 81372 eval capture: inner eval success is `data.result.success`, diagnostics `data.result.diagnostics`, and user return `data.result.result` (null for that void call). There is no extra result layer in that capture. This is Windows evidence, not Mac execution, and the captured command was eval. The package proves eval_file shares the evaluation path. Server transport success can contain an EvalResponse failure; check process status, outer success/errors, exact target/bound parameters, inner typed success and returned observer phase receipt separately.

File semantics: eval takes code; eval_file takes a file read by Unity, ending .cs, relative to Unity process cwd unless absolute. It is a method-body snippet, not a complete C# compilation unit. An explicit return supplies the result. The protocol does not hash/freeze/canonicalize the file for the caller. Error diagnostics are useful; success can omit compile warnings, and this execution implementation does not assign captured Output. Lean replies strip metadata; the inner command is hardcoded eval even for eval_file. Do not parse human tables, scrape log output or require exactly four DTO keys.

Timeouts have separate layers. CLI global timeout is seconds per the installed skill; eval and server request parameters use milliseconds. Actual CLI binding must be read back, not guessed. Dispatcher cancellation only prevents queued work; it does not abort work already started. The eval compiler does not cancel execution on the timeout argument. A timeout is an unknown side-effect outcome, not proof of rollback or a reason to repeat ARM.

Each eval gets a fresh GUID-named assembly/type. Recompiling identical lambda text cannot reliably remove an earlier callback. However, Windows reports its unrun observer496621 uses a supported same-domain solution: ARM stores the ORIGINAL Stop Action in an AppDomain slot; DISARM retrieves and invokes that object. Its closure captures and removes its original delegates, clears its key and closes its receipt writer. That avoids the fresh-assembly identity issue. We do not classify that observer as broken. [Delegate identity](https://learn.microsoft.com/en-us/dotnet/api/system.delegate.op_equality?view=netframework-4.8.1), [retaining anonymous handlers](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/events/how-to-subscribe-to-and-unsubscribe-from-events), and [AppDomain object storage](https://learn.microsoft.com/en-us/dotnet/api/system.appdomain.setdata?view=netframework-4.8.1) support this source-based inference.

AppDomain storage does not promise continuation through a real domain reload. The reported observer stops in beforeAssemblyReload and explicitly promises no after-reload continuation. A stable compiled bootstrap with durable pre/post receipts is a separate option; the package shows one in EditorConsoleCaptureBootstrap.cs22–47. Same-domain, duplicate-arm, timeout and reload controls remain pending. No private reflection, event-list surgery or GetCompanionScene access is proposed. CHECK/ARM/DISARM receipt invariants are documented separately; no observer code or controller is added here.
