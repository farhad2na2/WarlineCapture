# S002 library launch audit — 2026-09-23

Scope: S002, the fourth playable entry, not catalog S004. Reviewed checkout `511c034dc`, especially library-enablement commit `02c5344f9` (#50), its existing expanded runtime, authored map data, tests, retained evidence, and the user's opening-frame screenshot. This is an audit, not a repair.

## Verdict

Keep the scenario specification and reusable rules, but redo the runtime integration before treating S002 as a player-ready mission. This is a substantial integration repair, not just a camera tweak. The current implementation has ECS state, but bypasses the established entity-prefab spawning/rendering and movement paths. A wholesale deletion of the scenario/compiler/objective work is not justified.

## How it became selectable

The catalog now marks S002 Playable and assigns dispatch index 4. QuickGameConfig normalization preserves that index; the existing library enables Launch from IsPlayable. SkirmishLaunchProjection intercepts index 4, creates the expansion config set in memory, reads INITIAL_SETUP_MATRIX.csv from Design, compiles S002 Regular/Standard, and queues an expanded session. The expanded session stores map hint 0, which loads the existing Desert Base map. This is not a new fourth map.

The latest commit primarily exposes pre-existing expansion code. The separate GameObject presentation and direct movement implementation predate that enablement; they should not all be attributed to the latest change.

## Findings

### P1 — Deployment coordinates do not match the loaded map

`SkirmishMapLayoutConfig.cs:75` defines a 600×420 layout with origin (-300,-210). `SkirmishLayout_S002.asset:29` puts the player base at X=-228, Z=0 and staging at X=-192, Z=0. The visual service applies these coordinates directly to both GameObjects and LocalTransform; it does not convert them into the loaded map's coordinate system.

The Desert Base preset has no explicit operationMap reference, so `MatchSceneView.OperationMapLaunch.cs:74` uses the Desert Base catalog fallback. `Assets/Game/Scenes/Match.unity:196` references the compatibility catalog, whose Desert Base definition has world and camera bounds X=0..2048, Z=0..1024 (`OperationMap_Compatibility_DesertBase01.asset:25`). Thus the player deployment is outside the configured playable/camera area. An opening camera request at the player base cannot correctly frame this setup while respecting those bounds. This is a concrete spatial defect consistent with the blank opening screenshot; the exact sequence of camera requests was not reproduced live.

There is also a startup robustness issue: `SkirmishPresentationSystem.cs:46` marks a session focused even when Focus returns early because the base transform or camera request singleton is missing. It does not retry that initial focus.

### P1 — Unit presentation bypasses the established entity spawning path

`SkirmishScenarioSpawnSystem.cs:285` creates fresh ECS entities with scenario ownership, role, faction, and prefab-key data. `SkirmishRosterProjectionSystem` adds health and role overlays. These are real ECS entities, so the units are not solely GameObjects.

However, `SkirmishVisualSpawnService.cs:161` calls Object.Instantiate on a GameObject prefab for each visual and stores it in a managed SkirmishVisualInstanceRecord. `SkirmishWorldMovementService.cs:192` copies entity positions onto those GameObject transforms. This differs from `InitialUnitsSpawnSystem.cs:372`, which uses the shared entity spawn service. The separate expansion path is not evidence of compliant entity rendering merely because it uses ECS components. Replace this adapter with the shared baked/runtime entity prefab pipeline and verify animation, selection, rendering, death, and cleanup together.

### P1 — Movement bypasses obstacle-aware path following

`SkirmishWorldMovementService.cs:87` explicitly removes UnitPathFollow. It then advances LocalTransform directly toward the destination at a constant speed. This step performs no grid/obstacle/path waypoint checks. Requesting a shared path elsewhere does not fix this: the follow component is removed before movement.

Combat also has a separate overlay-based engagement service: `SkirmishExpandedEngagementService` checks range and applies health damage directly. A successful automated victory in this implementation does not certify parity with the game's normal navigation/combat presentation. Keep scenario orders and balance data, but reconnect them to the shared simulation systems.

### P1 — The HUD describes a different rules/economy model

`UiShellEcsGateway.Skirmish.cs:22` computes the clock using the legacy 900-second limit; line 80 displays the legacy 24-infantry cap. S002 Standard compiles against 1080 seconds and 48 infantry capacity (`INITIAL_SETUP_MATRIX.csv:5`). Consequently the screenshot's 14:51 and 20/24 are consistent with the wrong HUD values, not the S002 rules.

S002 separately seeds 900 materials, 240 oil, and 700 usable fuel. The material header reads FactionTacticalMaterialsComponent (`UiMatchHudResourceReadModelSystem.cs:37`), while the expansion's production/research read SkirmishEconomyStockComponent. No expansion-stock projection into that header was found. The screenshot's 0/0 materials is therefore an additional integration failure, not a trustworthy view of the expansion ledger. Unify or explicitly project the economy and capacity state used by HUD and player actions.

### P1 — Normal player launch depends on a repository-only CSV

`SkirmishLaunchProjection.cs:72` resolves the parent of Application.dataPath and reads `Design/Roadmap/Skirmish_Expansion/INITIAL_SETUP_MATRIX.csv`. `SkirmishSetupMatrixTable.cs:80` fails when that file is missing. This is not a Resources, Addressables, or StreamingAssets load. A normal packaged player cannot assume that repository directory exists. Launch must use packaged authored/compiled scenario data. The use of CreateInMemory also means this entry path does not load the authored S002 definition asset as its source of truth.

### P2 — Retained visual acceptance does not demonstrate gameplay readiness

The checked-in `_Evidence/s002-regular-standard-104731-playing.png` shows the main menu. Its sibling JSON reports phase Playing. This mismatch is directly visible; it does not establish intentional fabrication.

The capture helper checks SkirmishMatchState.Phase and captures without checking that the shell has completed entry into MatchHud (`SkirmishS002GameViewCapture.cs:144`). The expansion itself sets Playing immediately after ledger spawn, before visual attachment (`SkirmishScenarioSpawnSystem.cs:59`). The new library-dispatch test checks identity/configuration in an isolated ECS World, not loaded-map framing, entity rendering, navigation, HUD parity, or a packaged build. Existing terminal traces may validate their recorded simulated outcomes, but do not resolve these integration defects.

## What to retain and redo

Retain: S002 identity, roster/start-package specification, typed setup compiler and validation, objective/outcome rules, capacity/production accounting logic, deterministic configuration, localization, checkpoint contracts, and useful unit tests. Revalidate their adapters and lifecycle assumptions when integrating.

Redo: map-relative deployment, entity prefab spawning/rendering, shared navigation and combat integration, camera/readiness gating, HUD/economy projection, packaged content loading, and end-to-end acceptance evidence. Recommend keeping S002 unavailable as a normal playable until these pass; no catalog state was changed by this audit.

Acceptance should cover launch through the actual library, a visible base/army on the first playable frame, all spawns inside navigable map bounds, shared entity-rendering/animation components, movement around blocked terrain, selection/attack/hold/production/death, correct stocks/caps/deadline, restart/return cleanup, and a standalone build without the Design directory.

## Verification limits

Unity Pipeline connected successfully; Editor was out of Play mode and the console contained no retained errors. No mission was launched, no fresh gameplay/test pass is claimed, and no game code or assets were changed. Findings above are source/configuration and retained-image evidence; exact opening camera timing and full live interaction remain to be reproduced during repair.
